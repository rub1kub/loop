# Пакет для независимого аудитора

Сопровождает ZIP из `make contracts-audit-pack`. Формальные границы работы описаны в
[../audits/mainnet-audit-scope.md](../audits/mainnet-audit-scope.md); здесь — модель угроз,
карта «инвариант → чем уже доказан» и список вопросов, на которые нам нужен именно внешний ответ.

Цель документа — не убедить аудитора, что код верен, а сэкономить ему время на реконструкции
замысла и явно показать места, где мы сами не уверены.

## Что именно менялось

Аудит проходит по `DuelEscrow 1.4.0`. Относительно проверяемого ранее `1.3.0` изменено:

| Область  | Изменение                                                                                  |
| -------- | ------------------------------------------------------------------------------------------ |
| messages | `HolderFeePermit { validUntil, signature }` как maybe-ref в конце всех трёх open-сообщений |
| storage  | `OfferData.feeExempt: bool`                                                                |
| getters  | `contractConfig` дополнен `holderFeeSupported`                                             |
| логика   | `settleWinner` не удерживает комиссию, если у победителя `feeExempt`                       |
| errors   | `InvalidHolderPermit=134`, `HolderPermitExpired=135`                                       |
| домены   | добавлен `HOLDER_FEE_DOMAIN=0x4C4F4F63`                                                    |

`BankQueue 1.3.0` не менялся, но входит в область: он остаётся держателем пользовательских
обязательств.

## Модель угроз

Кого мы считаем противником и что он может:

| Актор                         | Возможности                                        | Чего не должен достичь                                       |
| ----------------------------- | -------------------------------------------------- | ------------------------------------------------------------ |
| Произвольный внешний адрес    | любые сообщения контракту, любой порядок и тайминг | забрать чужую ставку, изменить чужой шанс, заблокировать пул |
| Второй участник дуэли         | всё вышеперечисленное + владение своим offer       | предопределить исход, отменить чужой boost, уйти от расчёта  |
| Скомпрометированный backend   | подпись permit'ов, выдача intents, содержимое БД   | изменить исход, забрать средства, изменить чужой шанс        |
| Скомпрометированный owner     | pause, fee, treasury, смена owner, вывод surplus   | забрать `locked` и резерв, изменить исход дуэли              |
| Скомпрометированный провайдер | ложные ответы TON API                              | заставить контракт принять неверное состояние                |

Ключевое допущение продукта: **backend не является доверенным для исхода**. Он не может выбрать
победителя, изменить шанс или списать чужую ставку. v1.4 не должен был это допущение ослабить —
подтверждение этого и есть главный вопрос к аудиту.

Просьба перепроверить сами инварианты, а не только наши доказательства.

## Риски, по которым нам нужен внешний ответ

### R1 — один ключ подписи получил вторую власть

`inviteSignerPublicKey` подписывает и direct-invite permits, и holder-permits. Радиус поражения
при компрометации ключа вырос: раньше — навязывание пары в direct-вызове, теперь ещё и обнуление
комиссии произвольному offer. Пользовательские ставки по-прежнему недоступны, потери ограничены
доходом протокола.

**Вопрос:** приемлемо ли совмещение, или holder-permits должны подписываться отдельным ключом?
Разделение требует нового deployment, поэтому решение принимается до, а не после аудита.

### R2 — освобождение распространяется на весь пул

Победитель с `feeExempt` забирает пул целиком, включая boost соперника. Мы считаем это
намеренным («нулевая комиссия для держателей»), но следствие стоит проверить: в крупной дуэле
холдера против не-холдера протокол не получает ничего.

**Вопрос:** подтвердить, что это соответствует заявленной модели, и что тут нет способа
эксплуатации со стороны сговорившейся пары.

### R3 — проверка владения токеном происходит вне контракта

Контракт доверяет подписи, а владение PLUSH BRICK проверяет backend через Jetton-getter перед
подписанием. Скомпрометированный backend или лгущий провайдер выдаёт бесплатные permit'ы.
Потери ограничены доходом протокола; ставки и исход недостижимы.

**Вопрос:** согласны ли, что граница проведена в правильном месте, с учётом того, что
синхронная проверка Jetton-баланса в TVM невозможна.

### R4 — обоснование границы в 81 шаг аллокации BANK

`BANK_MAX_ALLOCATION_STEPS = 81` обосновано так: минимальная цель — `1 GRAM × 1.25`, максимальный
распределяемый остаток — около `99 GRAM`, отсюда не более 80 полных завершений плюс одна частично
наполненная позиция.

Обоснование опирается на неочевидный инвариант: **один депозит оставляет частично наполненной не
более одной позиции**, поэтому очередь не может накопить много почти-завершённых позиций. Если
инвариант нарушим, крупный депозит упрётся в лимит и будет отвергнут целиком, а при достаточном
числе таких позиций отвергаться начнут все депозиты — BANK перестанет принимать входы навсегда.
Мы не нашли последовательности, приводящей к этому, но уверенность здесь ниже, чем хотелось бы.

**Вопрос:** доказать или опровергнуть достижимость состояния, в котором очередь содержит более 81
позиции, каждая из которых завершается доступным остатком одного депозита.

### R5 — льготный settlement не доказан в сети

Canary-кошельки не держат PLUSH BRICK, поэтому финализированная транзакция подтверждает только
полнокомиссионный путь. Нулевая комиссия подтверждена тестами и живым getter'ом.

**Вопрос:** считать ли это блокирующим для mainnet, либо достаточно провести отдельный canary с
holder-кошельком до запуска.

### R6 — унаследованные продуктовые риски

BANK не имеет отмены и досрочного возврата, а его выплаты зависят от новых взносов. Это
осознанное продуктовое решение, зафиксированное в
[../agents/decisions-and-risks.md](../agents/decisions-and-risks.md), а не дефект реализации.

**Вопрос:** подтвердить, что реализация соответствует заявленному поведению, без оценки самой
экономической модели.

## Что уже прогнано и воспроизводимо

```bash
make contracts-mainnet-technical   # fork, coverage, gas baseline, mutation gates
make contracts-audit-pack          # детерминированный ZIP без секретов
.venv/bin/python scripts/verify-contracts.py --network testnet --require-smoke
```

Итог последнего прогона: контрактных тестов `73`, покрытие строк `99.67%`, ветвей `87.45%`,
mutation-порог DUEL critical `99.2%`, gas-профиль без дрейфа. Живые доказательства deploy, smoke
и двухкошелькового canary — в [`../../deployments/testnet/duel.json`](../../deployments/testnet/duel.json).

Автоматические проверки уменьшают известный риск и не доказывают отсутствие уязвимостей —
именно поэтому аудит и заказывается.

## Что мы просим на выходе

1. Отчёт в PDF с указанием проверенного commit.
2. Findings с severity и, для каждого, конкретным сценарием эксплуатации.
3. Явный вердикт по `R1`–`R5`.
4. Указание, какие инварианты из таблиц выше проверены, а какие остались вне области.

Отчёт кладётся в `docs/audits/`, его SHA-256 вписывается в `deployments/mainnet/release.json`;
`make contracts-mainnet-preflight` пересчитывает хеш файла и не пропустит несоответствие.
