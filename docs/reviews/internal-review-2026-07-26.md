## Метод

Ревью строилось не вокруг чтения диффа, а вокруг гипотез: для каждой формулировалось, какое
конкретно наблюдаемое поведение опровергнет её. Там, где гипотеза проверяема исполнением, писался
тест — потому что сегодняшняя сессия дала прямое свидетельство границ чтения: три дефекта
(`F4`–`F6`) не были видны при многократном перечитывании и вскрылись только при реальном
развёртывании.

## Проверенные гипотезы атак (опровергнуты)

### Holder-permit

| Гипотеза                                                           | Результат                                                               |
| ------------------------------------------------------------------ | ----------------------------------------------------------------------- |
| Permit переносится на другой offer                                 | отвергнут: `offerId` в преобразе; тест на границе                       |
| Permit переносится на другой кошелёк                               | отвергнут: `owner` в преобразе; тест на границе                         |
| Permit переносится на другую сеть/deployment                       | отвергнут: `networkId` + `contract.getAddress()` в преобразе            |
| Просроченный permit молча даёт полную комиссию                     | отвергнут: открытие целиком падает, значение не блокируется             |
| Вечный permit                                                      | отвергнут: верхняя граница `now + MAX_EXPIRY_DELAY`                     |
| Повторное использование того же permit                             | невозможно: `usedOfferIds` не даёт переиспользовать offer id            |
| Коллизия с direct-accept permit (`0x4C4F4F62` против `0x4C4F4F63`) | разные домены в первых 32 битах преобраза                               |
| Освобождение меняет шанс или boost-математику                      | не меняет: `feeExempt` читается только в `settleWinner`                 |
| Освобождение ломает сохранение стоимости                           | не ломает: `locked` уменьшается ровно на `totalPool`, столько же уходит |

### Совместимость после переключения

Отдельно проверен сценарий, который на mainnet будет стоить дороже всего — **закешированный
клиент после cutover**. Тест `a stale v1.3 client body is rejected without touching state`
отправляет байт-в-байт тело v1.3 (без завершающего maybe-бита) в контракт v1.4 и доказывает:

- транзакция падает с cell underflow (exit `9`) **до** любой записи в storage;
- `locked` остаётся `0`, значение не захватывается;
- offer id не попадает в `usedOfferIds` — тот же кошелёк тут же успешно открывает тот же offer.

Адреса контрактов bounceable, поэтому значение возвращается отправителю. Практический вывод:
пользователь со старым бандлом видит ошибку кошелька и повторяет действие, потерять средства
этим путём нельзя.

## Что изнутри не проверяется

1. **Корректность самой конструкции.** Я проверял код против собственного замысла. Если замысел
   неверен, ревью этого не покажет.
2. **Владение токеном.** Контрактный путь нулевой комиссии доказан живой транзакцией
   (`14c29b0d…`: пул `1.1 GRAM`, выплата `1.1 GRAM`, ноль сообщений комиссии). Но permit там
   подписан напрямую, поэтому проверка фактического владения PLUSH BRICK остаётся доказанной
   только API-тестами: сам токен живёт в mainnet, и на testnet эту половину замкнуть нечем.
3. **Экономическая устойчивость BANK.** Вне области кода.
4. **Соответствие законодательству.** Вне области кода и вне моей компетенции.
5. **Ответственность.** Отчёт без подписавшего его лица не даёт пользователю и регулятору того,
   на что можно сослаться.

## Второй проход: состязательные субагенты

После первого прохода запущены четыре независимых агента с чистым контекстом и разными
установками: сломать границу аллокации BANK, доказать её, атаковать контракт DUEL, атаковать
backend permit'ов. Свои выводы им не передавались, чтобы не получить эхо собственных рассуждений.
Это не независимость внешнего аудитора — та же модель, вероятно те же слепые зоны, — но чистый
контекст и установка «ломать» дали результат.

Найдено и исправлено четыре дефекта в backend, ни одного эксплуатируемого в контрактах:

| ID  | Дефект                                                                      | Класс                 | Статус     |
| --- | --------------------------------------------------------------------------- | --------------------- | ---------- |
| F7  | владение jetton принималось со слов индексатора, без привязки к мастеру     | обход комиссии        | исправлено |
| F8  | worker проверял подпись permit'а, но не срок, вопреки собственному правилу  | defense-in-depth      | исправлено |
| F9  | формат сообщения выводился из флага фичи, а не из возможностей контракта    | простой всех дуэлей   | исправлено |
| F10 | выплата проецировалась по комиссии из котировки, а не наблюдённой в цепочке | заклинивание проекции | исправлено |

`F9` — худший по последствиям: выключение holder-фичи на живом v1.4 заставило бы клиента слать
тело v1.3, которое контракт отвергает, и все открытия дуэлей умерли бы при healthy-статусе API.

Атака на контракт DUEL не дала эксплуатируемых находок: 18 атак отбиты, включая перенос permit'а
между деплоями и сетями, подмену домена, обход `feeExempt` через write-back в `AcceptDirectOffer`,
нарушение сохранения стоимости при двусторонних бустах и корректность выбора победителя на 40
раундах. Суита сохранена как `tests/duel_adversarial.test.tolk`.

По BANK обе противоположные установки сошлись: граница 81 верна, но недостижима — раньше
кончается газ. Подробности в `R4`.
