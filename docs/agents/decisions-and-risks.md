# Решения, полномочия и риски

Этот документ фиксирует не только устройство кода, но и намеренные продуктовые решения. Он нужен,
чтобы агент не «исправил» сознательно выбранное поведение и не выдал будущую идею за работающую
функцию.

## Принятые решения

### LOOP не является кошельком

- пользовательские ключи, seed-фразы и средства остаются во внешнем кошельке;
- TON Connect подтверждает владение и отправляет сообщения контрактам;
- PostgreSQL не является балансом или финансовым ledger;
- UI не должен превращаться в wallet/portfolio clone.

### BANK — открыто описанная финансовая пирамида

- новые взносы финансируют более ранние позиции;
- движение очереди и выплата не гарантированы;
- подтверждённую позицию нельзя отменить;
- ограничение начального размера снижает концентрацию первых позиций, но не устраняет риск;
- формулировка риска должна быть короткой и понятной, а не спрятанной в юридическом тексте.

Это не дефект, который можно заменить резервной выплатой backend: такое изменение сломало бы
экономику и потребовало бы нового контракта.

### DUEL — игра с риском и прозрачными шансами

- новый матч начинается `50/50`;
- шанс меняется только видимыми подтверждёнными boosts участников;
- диапазон ограничен `90/10`;
- сервер не выбирает победителя;
- no-reveal даёт преимущество раскрывшему, а при нуле reveals возвращает ставки;
- PLUSH BRICK не повышает шанс.

Ассоциация с азартной игрой не маскируется, но интерфейс не должен гарантировать выигрыш,
прятать вероятность или использовать манипулятивное срочное пополнение.

### Рейтинг измеряет надёжность, не богатство

Ставка, прибыль, баланс, победы и поражения не увеличивают score. Рейтинг строится из
подтверждённых завершений, своевременного reveal и квалифицированных друзей.

### Browser и Telegram — разные поверхности

- обычный посетитель `/` видит лендинг;
- пользовательский продукт требует подписанный Telegram `initData`;
- `/control` — отдельный браузерный owner-интерфейс;
- browser fallback не подделывает Telegram identity.

### PLUSH BRICK: утверждённая mainnet-модель

Решение владельца (2026-07-26): нулевая комиссия DUEL для держателей и ручные рыночные выкупы —
это действующая mainnet-модель, а не черновая идея.

Исполнение:

- нулевую комиссию реализует активный DuelEscrow v1.5: quote выдаёт подписанный LOOP holder permit,
  привязанный к сети, контракту, offer и адресу; при валидном permit победителя контракт не
  удерживает комиссию;
- включение отдельным флагом допустимо только после startup-проверки поддержки permit живым
  bytecode — иначе котировка разойдётся с фактическим списанием;
- выкупы выполняются вручную из казначейства; автоматического процесса нет, но каждая сделка
  обязана попасть в публичный журнал `docs/plush-brick-buybacks.md` с хешом транзакции —
  заявление без записи считается необоснованным;
- новая версия контракта должна сохранять holder-permit и повторно пройти release gates.

## Полномочия владельца

Owner обоих контрактов может:

- приостановить новые входы;
- пополнить резерв;
- изменить fee в пределах `0–10%`;
- изменить treasury;
- передать ownership;
- вывести средства в treasury в пределах правил каждого контракта.

Ограничения:

- withdrawal требует pause;
- destination фиксирован текущим treasury;
- DUEL защищает `locked + 0.2 GRAM`; BANK намеренно защищает только `0.2 GRAM` и позволяет owner
  вывести остальное даже при открытых позициях;
- DUEL fee меняется только при `locked=0`;
- pause не отключает cancel/expiry/reveal/settlement;
- backend и `/control` только готовят сообщение — финальная власть у owner-signed transaction и
  on-chain проверок.

Owner не может изменить исход DUEL. В BANK код технически позволяет вывести средства, на которые
рассчитывают открытые позиции; обязательства перед участниками от этого не исчезают.

## Основные риски

| Риск                               | Последствие                                   | Защита / статус                             |
| ---------------------------------- | --------------------------------------------- | ------------------------------------------- |
| BANK перестал получать новые входы | позиции зависают без срока                    | явный риск; автоматического bailout нет     |
| Потерян DUEL secret/device         | пользователь может пропустить reveal          | SecureStorage; recovery по deadline         |
| Оба не раскрыли                    | возврат principal                             | permissionless `ExpireDuel`                 |
| Provider недоступен                | intents остаются pending                      | retry/backoff, checkpoint не продвигается   |
| Wallet callback без finality       | ложное ожидание успеха                        | callback не меняет финансовый state         |
| Повтор/гонка сообщений             | двойная запись или расход                     | IDs, revisions, unique indexes, replay maps |
| Compromised invite signer          | риск поддельных direct permits                | pause; signer immutable, новый deployment   |
| Owner credential compromised       | изменение конфигурации в разрешённых пределах | pause/monitoring; on-chain limits           |
| Ошибка worker projection           | UI расходится с TON                           | exact message checks, savepoints, replay    |
| Mainnet без внешнего аудита        | неизвестный риск реальных средств             | disclosure, лимиты, canary и monitoring     |
| Ошибка holder permit               | неверная комиссия победителя                  | domain binding, live capability attestation |
| Регуляторные требования            | ограничения запуска по юрисдикции             | вне кода; нужна отдельная legal review      |

## Доказательства и их пределы

Доказано автоматическими проверками:

- детерминированные финансовые ветки контрактов;
- высокий coverage и mutation score;
- live mainnet bytecode/configuration;
- конкретные finalized BANK/DUEL сценарии;
- backend/frontend auth, bounds, idempotency и message construction;
- dependency audit на момент проверки.

Не доказано:

- отсутствие всех возможных уязвимостей;
- экономическая устойчивость BANK;
- соответствие законам любой юрисдикции;
- отсутствие неизвестных дефектов активного mainnet deployment;
- будущая периодичность или влияние ручных PLUSH buyback;
- независимость двух Telegram-аккаунтов в реферальной системе.

## Когда требуется новый контракт

Новый deployment обязателен, если меняются:

- storage layout или message ABI;
- экономическое правило BANK/DUEL;
- network/address domain;
- direct invite signer;
- способ расчёта fee, payout, chance или winner;
- права owner или withdrawal boundary;
- участие PLUSH BRICK в расчёте комиссии.

Backend-only изменение не может легитимно заменить on-chain правило.

## Mainnet решение

Текущий статус: **готово к независимому аудиту, не готово к запуску реальных средств**.

Решение GO возможно только при одновременном выполнении:

1. независимый аудит точного clean commit завершён;
2. report и SHA-256 находятся в Git;
3. `release.json` совпадает с audited commit;
4. mainnet contracts развёрнуты paused и empty;
5. source verification опубликована;
6. BANK shadow payout и DUEL two-wallet canary финализированы;
7. старые обязательства drained;
8. post-deploy verifier и runtime environment gate прошли;
9. операционный мониторинг и recovery rehearsed;
10. владелец отдельно принимает экономический и юридический риск.

Любое изменение reviewed source, compiler, owner, treasury, signer, limits или addresses после
аудита возвращает решение в NO-GO до повторного sign-off.

## Решения 1–2 августа 2026

Здесь фиксируются решения, принятые при переходе в mainnet. Каждое из них выглядит как ошибка для
агента, который читает только код, — поэтому записано с причиной.

### Владелец может вывести из BANK средства, на которые рассчитывают позиции

Было: `withdrawableBalance = баланс − lockedFunding − резерв`, то есть наполнение открытых позиций
защищено контрактом.

Стало: `withdrawableBalance = баланс − резерв`.

Причина: владелец обнаружил, что не может вернуть тестерам их деньги, когда очередь встала, и
потребовал возможности вывести любую сумму. Возражение о том, что это снимает главную гарантию
BANK, было высказано и отклонено осознанно: «НУ И ПУСКАЙ ЭТО БУДЕТ ВИДНО В ИСХОДНИКАХ / МЫ НИЧЕГО
НЕ СКРЫВАЕМ / Я ПУБЛИЧНОЕ ЛИЦО».

Компенсации: исходники опубликованы и проверены; в `docs/no-audit-disclosure.md` убрана строка о
защите заблокированных средств и добавлен раздел о полномочиях владельца прямым текстом; в BANK
добавлен `BankRefundPosition`, чтобы возврат конкретному человеку не требовал вывода всей кассы.

**Не восстанавливай старое поведение** как «исправление уязвимости». В DUEL защита ставок
осталась — там правку не делали.

### Лестница лимитов по правилу 5N

Было: три жёстких порога (5 → 10 → 15 GRAM) плюс расширение каждые 250 выплат.

Стало: ступень N GRAM открывается после 5N выплат, ступени 1..100.

Причина: владелец захотел, чтобы потолок начинался с 1 GRAM и рос «по-умному». Правило выбрано из
арифметики очереди: позиция на N GRAM с целью x2 требует ~2.2N последующих взносов, значит 5N
выполненных выплат держит худший затор примерно на половине пройденной истории.

Верхняя ступень 100, а не выше, потому что цикл распределения ограничен 81 шагом по газу, и предел
приходится на 112 GRAM.

Симуляция дала линейные 2.23 участника на позицию; десять выплат при цели x2 — это ~23 вкладчика,
при x1.25 — ~14.

### Возвраты конкретным людям не делаются

На снятом контракте остались три позиции. Владелец сказал: «не надо никому ничего возвращать».
Ранее отдельно: «Flayni ничего не возвращай».

Это решение, а не забытая задача. Обязательство перед этими людьми существует, но оно личное и
внеконтрактное.

### Открытие переносилось дважды

Обещание «на выходных» не выполнено. Дата назначалась на 8 августа 19:00 МСК, затем перенесена на
5 августа 19:30 МСК (среда). Владелец заявил, что второго промаха не будет.

Из этого следует правило: `LOOP_LAUNCH_AT` — публичное обещание, а не настройка. Менять только по
явной просьбе.

### Аудита не будет — подтверждено

Решение от 2026-07-27 осталось в силе при переходе на реальные деньги. Гейт `self_reviewed`
работает: раскрытие с закреплённым SHA-256, состязательный ревью, баунти с контактом и суммой,
лимит 1 GRAM вместо 10.

Требование 30 дней в testnet владелец отменил 2026-08-01.

### Раскрытие рисков не выносится в README

Владелец попросил убрать из README упоминания отсутствия аудита и перечень полномочий владельца:
«мы это же всем показываем». Формулировка «финансовая пирамида» и предупреждение об остановке
выплат в README остались.

Раскрытие живёт в `docs/no-audit-disclosure.md`, его SHA-256 закреплён в `release.json` и в
окружении production. Не переноси его обратно на первую страницу и не удаляй из `docs/`.
