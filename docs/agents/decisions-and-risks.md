# Решения, полномочия и риски

Этот документ фиксирует не только устройство кода, но и намеренные продуктовые решения. Он нужен,
чтобы агент не «исправил» сознательно выбранное поведение и не выдал будущую идею за работающую
функцию.

## Принятые решения

### LOOP не является кошельком

- пользовательские ключи, seed-фразы и средства остаются во внешнем кошельке;
- TON Connect подтверждает владение и отправляет сообщения контрактам;
- PostgreSQL не является балансом или финансовым ledger;
- UI не должен превращаться в wallet/portfolio clone.

### BANK — открыто описанная финансовая пирамида

- новые взносы финансируют более ранние позиции;
- движение очереди и выплата не гарантированы;
- подтверждённую позицию нельзя отменить;
- ограничение начального размера снижает концентрацию первых позиций, но не устраняет риск;
- формулировка риска должна быть короткой и понятной, а не спрятанной в юридическом тексте.

Это не дефект, который можно заменить резервной выплатой backend: такое изменение сломало бы
экономику и потребовало бы нового контракта.

### DUEL — игра с риском и прозрачными шансами

- новый матч начинается `50/50`;
- шанс меняется только видимыми подтверждёнными boosts участников;
- диапазон ограничен `90/10`;
- сервер не выбирает победителя;
- no-reveal даёт преимущество раскрывшему, а при нуле reveals возвращает ставки;
- PLUSH BRICK не повышает шанс.

Ассоциация с азартной игрой не маскируется, но интерфейс не должен гарантировать выигрыш,
прятать вероятность или использовать манипулятивное срочное пополнение.

### Рейтинг измеряет надёжность, не богатство

Ставка, прибыль, баланс, победы и поражения не увеличивают score. Рейтинг строится из
подтверждённых завершений, своевременного reveal и квалифицированных друзей.

### Browser и Telegram — разные поверхности

- обычный посетитель `/` видит лендинг;
- пользовательский продукт требует подписанный Telegram `initData`;
- `/control` — отдельный браузерный owner-интерфейс;
- browser fallback не подделывает Telegram identity.

### PLUSH BRICK: намерение и текущая реализация разделены

Продуктовая идея:

- режим без комиссии для holder;
- часть доходов LOOP направляется на рыночный buyback.

Фактическая реализация:

- API проверяет mainnet Jetton balance и показывает holder status;
- действующий DuelEscrow имеет одну глобальную fee;
- `fee_discount_active=false`;
- автоматического buyback-процесса, treasury policy и публичного proof пока нет.

До отдельного дизайна и контрактной/операционной реализации нельзя считать нулевую комиссию и
buyback выполненными функциями.

## Полномочия владельца

Owner обоих контрактов может:

- приостановить новые входы;
- пополнить резерв;
- изменить fee в пределах `0–10%`;
- изменить treasury;
- передать ownership;
- вывести только свободный surplus в treasury.

Ограничения:

- withdrawal требует pause;
- destination фиксирован текущим treasury;
- `locked + 0.2 GRAM` недоступны для вывода;
- DUEL fee меняется только при `locked=0`;
- pause не отключает cancel/expiry/reveal/settlement;
- backend и `/control` только готовят сообщение — финальная власть у owner-signed transaction и
  on-chain проверок.

«Полный доступ» не означает право забрать пользовательские обязательства или изменить исход
DUEL.

## Основные риски

| Риск                               | Последствие                                   | Защита / статус                             |
| ---------------------------------- | --------------------------------------------- | ------------------------------------------- |
| BANK перестал получать новые входы | позиции зависают без срока                    | явный риск; автоматического bailout нет     |
| Потерян DUEL secret/device         | пользователь может пропустить reveal          | SecureStorage; recovery по deadline         |
| Оба не раскрыли                    | возврат principal                             | permissionless `ExpireDuel`                 |
| Provider недоступен                | intents остаются pending                      | retry/backoff, checkpoint не продвигается   |
| Wallet callback без finality       | ложное ожидание успеха                        | callback не меняет финансовый state         |
| Повтор/гонка сообщений             | двойная запись или расход                     | IDs, revisions, unique indexes, replay maps |
| Compromised invite signer          | риск поддельных direct permits                | pause; signer immutable, новый deployment   |
| Owner credential compromised       | изменение конфигурации в разрешённых пределах | pause/monitoring; on-chain limits           |
| Ошибка worker projection           | UI расходится с TON                           | exact message checks, savepoints, replay    |
| Mainnet без аудита                 | неизвестный риск реальных средств             | release gate fail-closed                    |
| PLUSH обещание раньше реализации   | вводящее в заблуждение ожидание комиссии      | явно разделять intended/current             |
| Регуляторные требования            | ограничения запуска по юрисдикции             | вне кода; нужна отдельная legal review      |

## Доказательства и их пределы

Доказано автоматическими проверками:

- детерминированные финансовые ветки контрактов;
- высокий coverage и mutation score;
- live testnet bytecode/configuration;
- конкретные finalized BANK/DUEL сценарии;
- backend/frontend auth, bounds, idempotency и message construction;
- dependency audit на момент проверки.

Не доказано:

- отсутствие всех возможных уязвимостей;
- экономическая устойчивость BANK;
- соответствие законам любой юрисдикции;
- безопасность mainnet deployment, которого ещё нет;
- работоспособность PLUSH fee-free/buyback-модели;
- независимость двух Telegram-аккаунтов в реферальной системе.

## Когда требуется новый контракт

Новый deployment обязателен, если меняются:

- storage layout или message ABI;
- экономическое правило BANK/DUEL;
- network/address domain;
- direct invite signer;
- способ расчёта fee, payout, chance или winner;
- права owner или withdrawal boundary;
- участие PLUSH BRICK в расчёте комиссии.

Backend-only изменение не может легитимно заменить on-chain правило.

## Mainnet решение

Текущий статус: **готово к независимому аудиту, не готово к запуску реальных средств**.

Решение GO возможно только при одновременном выполнении:

1. независимый аудит точного clean commit завершён;
2. report и SHA-256 находятся в Git;
3. `release.json` совпадает с audited commit;
4. mainnet contracts развёрнуты paused и empty;
5. source verification опубликована;
6. BANK shadow payout и DUEL two-wallet canary финализированы;
7. старые обязательства drained;
8. post-deploy verifier и runtime environment gate прошли;
9. операционный мониторинг и recovery rehearsed;
10. владелец отдельно принимает экономический и юридический риск.

Любое изменение reviewed source, compiler, owner, treasury, signer, limits или addresses после
аудита возвращает решение в NO-GO до повторного sign-off.
